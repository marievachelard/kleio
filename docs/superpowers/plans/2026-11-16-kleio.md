# Kleio Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Une web app installable sur iPhone qui envoie chaque jour à 08:30 (Europe/Paris) une notification sur un fait historique, avec un écran de détail et un calendrier qui ne montre que les jours déjà passés.

**Architecture:** Un seul Cloudflare Worker (TypeScript) sert l'API, déclenche l'envoi quotidien (Cron Trigger) et héberge les fichiers statiques de la PWA (JavaScript sans framework). Les faits sont des fichiers JSON versionnés, embarqués dans le Worker et jamais publics : l'API ne renvoie que les jours dont la date est passée. L'unique inscription push est stockée dans KV.

**Tech Stack:** TypeScript, Cloudflare Workers (static assets, Cron Triggers, KV), Wrangler, Vitest, happy-dom, une bibliothèque Web Push compatible Workers (`@block65/webcrypto-web-push`, à confirmer à l'installation), GitHub Actions.

- Écran de détail, dans cet ordre : l'essentiel, le contexte, « Le saviez-vous », bloc d'invitation avec bouton « Lire l'article », ligne « Source : <site> » cliquable en bas. Si des années précédentes existent pour la même date : section « Aussi un 16 novembre » (date adaptée).

- En-tête des écrans Détail et Calendrier : « Kleio » centré, en texte de la couleur de lien (`#A94A43` en clair, `#E08A83` en sombre), sans logo, seul sur sa ligne ; sur le Détail, le bouton « ‹ Calendrier » est sur la ligne du dessous, à gauche.
- Calendrier : historique uniquement ; deux flèches (et un glissement horizontal) changent de mois entre le mois du lancement et le mois en cours, la flèche précédente grisée dans le mois du lancement et la suivante dans le mois en cours ; l'année s'affiche à côté du nom du mois. Premier jour = date de lancement. Les jours futurs sont grisés et non touchables. Le jour touché s'affiche dans une carte sous la grille, un petit bouton carré arrondi couleur clé avec une flèche ↗ foncée (même style que « Lire l'article »), aligné sur la ligne du titre de la carte, ouvre le détail. Le bouton de retour du détail s'appelle « ‹ Calendrier » ; le calendrier n'a pas de bouton « ‹ Aujourd'hui ». Dates incontournables marquées d'une étoile « ★ ».
- Les faits des jours à venir ne sont jamais renvoyés par l'API ni présents dans les fichiers statiques ou le cache du service worker.
- Copie : jamais de « · », jamais de tiret long « — », jamais « fun fact ». Titre d'anecdote : « Le saviez-vous ».
- Aucune notification vide : sans fait prêt pour le jour, rien n'est envoyé.
- Jamais de secret (clé privée VAPID, clé d'accès, jeton Cloudflare) dans le dépôt.
- Les actions visibles de l'extérieur (créer le dépôt GitHub, créer des secrets, déployer) se font seulement après un accord explicite de Marie dans la conversation.

## Review Focus

1. Changement d'heure (dernier dimanche de mars et d'octobre) : les deux crons UTC (`30 6 * * *` et `30 7 * * *`) ne doivent produire qu'une seule notification, à 08:30 heure de Paris. Test : `shouldSendNow` sur les deux jours de bascule.
2. Déclenchement en double ou en retard du cron : pas de seconde notification le même jour (idempotence via KV), et un retard de quelques minutes reste accepté.
3. Jour sans fait : aucune notification, pas d'erreur, le statut indique « aucun fait prêt ».
4. Inscription expirée (réponse 404 ou 410 du service push) : marquée invalide, visible dans le statut, et l'app propose de se réinscrire.
5. Dates : le serveur décide de « aujourd'hui » (Paris), jamais l'horloge du téléphone. Une URL directe vers un jour futur renvoie 404 sans contenu. Le 29 février n'existe que les années bissextiles.
